# 词表生成工具

支撑「点译文里的词 → 看读音和意思」这个功能。

## 核心设计：LLM 只在 CI 跑一次

```
飞书表格 ──(你改数据时)──> GitHub Actions ──> LLM 生成一次 ──> words.json ──> CDN
                                                                              │
                                                    App 查本地 Map <──────────┘
```

**App 端永远不调用 LLM。** 用户点一万次词也是 **0 token**、0 网络、0 延迟。
唯一花钱的时刻是你**加了新梗**，那时重跑一次；而且数据没变时脚本会**直接短路跳过**，
连那一次调用都省了。

## 为什么不用实时词典 API

要支持点词查询，每种语言其实需要**三件事**，而且各不相同：

| | 分词 | 读音 | 释义 |
|---|---|---|---|
| 英语 | 空格即可 | IPA 音标 | 英汉词典 |
| 日语 | **需要分词** | 假名 | 日汉词典 |
| 中文 | **需要分词** | 拼音 | —— |

中日文没有空格，**"用户点的是哪个词"App 自己判断不了**。再加上免费 API 关停/改接口/加限额
是常态，维护三套接口的成本远高于一次性生成。

## 关键简化：App 端零分词算法

词表生成时就把**词边界**定好了，App 只需要按已有词表匹配：

- **英语**：按字母序列切（连字符和撇号算词内，所以 `laid-back` / `I'm` 是一个词）
- **日语**：贪心最长匹配 —— 从当前位置尝试最长的词

因为词表就是从同一批语料生成的，边界已知，贪心匹配必然落在正确的位置上。
`verify.mjs` 就是用来验证这一点的。

## 文件

| 文件 | 作用 |
|---|---|
| `generate.mjs` | 读 `data/memes.json`，产出/更新 `data/words.json` |
| `verify.mjs` | 校验覆盖率：哪些词点不动、贪心分词是否落在预期边界 |

## 成本与容错

- **数据没变** → 比对 `_meta.sourceHash`，直接退出，**0 token**
- **有新梗** → 只补缺失的词，**已有词条一律保留**（不会覆盖你手工修正的内容）
- **没配 LLM** → 保留现有词表并报告缺了什么，**不报错**
- **LLM 调用失败** → 词表不修改，工作流标记该步骤失败但不阻塞梗数据同步

`generate.mjs` 支持两个 provider，按顺序回退：

| 优先级 | Provider | 需要什么 |
|---|---|---|
| 1 | DeepSeek | `DEEPSEEK_API_KEY`（放在 GitHub Secrets） |
| 2 | GitHub Models | Actions 内置的 `GITHUB_TOKEN`，**免费、无需额外配置** |

## 词表格式

```jsonc
{
  "_meta": {
    "sourceHash": "99573c8d2b02d437",   // 对应哪一版 memes.json
    "updatedAt": "2026-10-10T12:00:00.000Z",
    "generator": "GitHub Models/openai/gpt-4o-mini"
  },
  "en": {
    "eternal": { "reading": "/ɪˈtɜːrnl/",  "zh": "永恒的；不朽的" }
  },
  "ja": {
    "永遠":     { "reading": "えいえん",    "zh": "永远；永恒" }
  }
}
```

**可以手工编辑。** 自动流程只添加缺失的词，不会动已有的。

## 手工补词

不想跑 LLM 也行 —— 直接改 `data/words.json`，格式照上面填。然后：

```bash
node tools/words/verify.mjs                 # 确认没有点不动的词
cp data/words.json app/src/main/assets/words.json   # 同步到内置兜底
```

中文没有词表（母语不查），所以只有 `en` 和 `ja` 两棵。
